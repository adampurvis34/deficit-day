# Nutrient Density Reference

Per **100 g** of food **in the state listed**. Values are USDA FoodData Central
(SR Legacy / Foundation Foods) rounded to logging precision.

Every row satisfies the Atwater check — `P×4 + C×4 + F×9` lands within a few percent of
the kcal column, with the residual explained by fiber and rounding.

> **State matters.** Rows marked *(cooked)* assume cooked weight. Rows marked *(dry)* or
> *(raw)* assume that state. Mixing these up on rice or pasta is a 2-3× error.
> Conversion factors are in `portion-anchors.md` §6.

## Fiber — needed for the Atwater check on vegetable-heavy meals

Fiber sits inside the `C` column (that's "carbohydrate by difference", how USDA and food
labels report it), but it yields ~2 kcal/g rather than 4. For most meals this is noise.
For a plate that's mostly vegetables it is not — the uncorrected arithmetic can overstate
calories by 20%+ and trip the calculator's reconciliation gate for entirely legitimate
reasons.

When a meal is vegetable- or legume-heavy, set `fiber_g` on those components and the
calculator corrects for it.

naive Atwater check purely because of fiber, and alcohol rows read ~100% "low" because
ethanol isn't a macro. Both are correct behaviour, not errors in the data. Everything
else in this table reconciles within a few percent.

## When this table is not enough

1. **Packaged food** — read the label. It beats any database.
2. **Chain restaurant** — they publish nutrition data. Use it; it is far better than
   estimating, even though it carries its own ±20% preparation variance.
3. **Anything else** — USDA FoodData Central: `scripts/usda_lookup.py`, free API key
   from <https://fdc.nal.usda.gov/api-key-signup/>. Prefer `Foundation` and `SR Legacy`
   data types over `Branded`, which is user-submitted and noisier.
